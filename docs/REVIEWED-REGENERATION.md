# Reviewed regeneration — milestone 5

Existing Prototype and Capability identities are retained. Full generation, recalculation, methodology-triggered generation and downstream regeneration return a pending proposal for existing work. Initial generation is the only path that creates a complete new tree without a proposal. Compatibility confirmation flags cannot authorize replacement.

## Identity and preservation

Newly generated records receive structural keys and the exact generated field baseline. Future proposals change a generated field only when its current value still equals that baseline. Authored fields, manual records, approved criteria, sprint-assigned stories and release-linked features are preserved. Scheduling, assignments, Jira links and phase overrides are not regenerated by proposal application.

Legacy feature/root/phase identity is reused only where an explicit canonical reference or structural discriminator is unambiguous. Historical stories and criteria are not matched by title. A mapping decision establishes identity while preserving content; it does not invent a historical baseline. Ambiguous candidates are shown for review. Missing-source records remain intact with a review status; archived records are not resurrected. No automatic archival is performed.

## Review contract

- POST `/api/initiatives/:id/regeneration-proposals` creates `{prototypeId, proposalId, status: pending}` without changing live planning records.
- GET the collection or `/api/initiatives/:id/regeneration-proposals/:proposalId` retrieves frozen impact, before/proposed values, preserved fields, candidate records, expected record revisions, retained delivery IDs and fingerprints. These surfaces require initiative editing authority.
- POST to the proposal ID requires `expectedFingerprint` and exactly one decision for each item: `keep`, `apply` an eligible addition/generated field change, or `map` to an eligible existing candidate. Every UI decision defaults to keep. Parent identity must be available before a child is added.
- Application rechecks current membership/action, source and record fingerprints, then records the checkpoint, changes, orphan review flags, selected decisions, resulting key-to-ID map and audit evidence in one serializable transaction. It rejects stale or repeated applications. Changed plans return to draft for final approval; delivery assignments remain intact.

The proposal payload, source binding, author and fingerprints are immutable in PostgreSQL. The pending-to-applied transition is one-way. RLS excludes viewers, external stakeholders and other workspaces. Existing user/service context wrappers and API origin/logging/rate-limit controls remain in force.

Jira remains read-only. Proposal generation/application performs no provider requests and grants no export approval.
