# Clarivia navigation inventory and proposed ownership

Reviewed against the current sidebar (`LeftNav.tsx`), route pages, and their principal UI components on 2026-11-09. This describes implemented surfaces, not a promise that every workflow is complete. `/initiatives/:id` below means the initiative selected by the current URL, or the first accessible initiative when the user is on a global page.

**Implementation update (2026-11-09):** The navigation was regrouped after this baseline inventory was written. Home, Projects, and Five-tool guide are the top links. Plan contains an Initiatives subsection (All initiatives, New initiative, Initiative brief), Requests & Priorities, Features & Backlog, Stories & Criteria, Refinement, Roadmap, Documents, Review regeneration, Feature hierarchy, Teams & Stakeholders, and Integrations. Deliver contains a Sprint subsection (Sprint Planning, Sprints & Releases, Sprint Review), Demos, PO Validation, Capacity & Cost, and Release Readiness. Learn contains Feedback, Risks & Blockers, Decisions, Activity, Matrix Portal, and Reports. Account settings is fixed to the bottom of the sidebar. The workspace horizontal link strip is limited to Roadmap; Roadmap's existing views and controls were not changed. The table below remains a record of what each route does; its proposed-placement column predates this approved grouping.

## What the user sees today

The sidebar contains 30 destinations across Start, Planning, Delivery, and Workspace. Home uses a six-link quick menu and puts the full sidebar in **All tools**. Roadmap uses the same quick menu with a narrower sidebar. Other pages show the full menu. Initiative workspace pages also show a horizontal tab strip; its labels and destinations are not fully aligned with the sidebar.

The application shell is shared, but the presentations differ by route. Home has a white main surface and light header; Demos has a dark header, tinted main surface, workspace header, and a separate demo board. These are intentional branches in `AppShell`, `TopHeader`, `LeftNav`, and the workspace layout. Each link also navigates to a distinct server-rendered route. That alone does not establish the cause of slowness. The root layout loads the user, authorization, initiatives, and permissions; the workspace layout loads the workspace and other context; Demos then loads its own records. All are dynamic. Measure navigation and query timing before attributing latency to the number of pages or merging routes for performance.

## Navigation decisions to finalize

1. Use **one shell contract** for every authenticated route: same sidebar width/sections, header treatment, page title, initiative switcher, content background, and loading pattern. The content panels may differ. Home can have different widgets without presenting as a separate product. Roadmap's compact sidebar should be evaluated under this same contract.
2. Keep the global destinations separate from initiative work. Global: Home, Projects, Initiatives, portfolio Risks & Blockers, portfolio Decisions, and organization settings. Initiative: Requests, Initiative brief, Features & Backlog, Stories & Criteria, Roadmap, delivery, feedback, and reports. A global page should never silently use the first initiative for an initiative-scoped link; require a selected initiative or prompt selection.
3. Give every concept one primary owner. Requests are incoming asks; Features & Backlog is approved planning work; Generated hierarchy is a secondary view. Demo agenda is preparation/outcomes for the Sprint Review, while PO Validation is acceptance against criteria. The guide, creation, regeneration, and account settings should not consume equal sidebar rank with daily work.
4. Proposed sidebar: **Home / Projects / Initiatives**; within an initiative, **Plan** (Requests, Initiative brief, Features & Backlog, Stories & Criteria, Roadmap), **Deliver** (Sprint Planning, Sprints & Releases, Sprint Review, PO Validation, Release Readiness), **Learn** (Feedback, Reports); **Organization** (Teams & Stakeholders, Integrations, Risks & Blockers, Decisions). Put supporting pages in their owners as specified above. Keep the initiative switcher visible across these routes.
5. Align the horizontal tabs with this map or remove the duplicate strip. Today its `BASE_TABS` includes `features` as “Feature Hierarchy,” but rendering rewrites that link to `/backlog` and labels it “Features & Backlog.” Its current-tab logic still treats `/workspace/features` as a separate tab. This is a concrete source of inconsistent naming and active-state behavior.
6. Profile Home → Demos and Demos → Home separately. Record server response time, root layout data time, workspace layout data time, page query time, and client transition time. Then optimize repeated data loading or cache boundaries based on evidence. Consolidating the sidebar by itself will improve clarity, but is not a measured performance fix.
