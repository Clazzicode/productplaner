# Feature-led navigation and assistance — milestone 7

Every authenticated account uses the same Product Owner workflow. The released Back/Forward history, parent links, section switcher, unsaved-change guard and mobile keyboard drawer remain. Planning navigation and the shell no longer depend on generation status or a historical qualifying profile.

The approved earlier five-tool guide was reviewed and reused as individual files: Initiative; Features & Backlog; Stories & Acceptance Criteria; Roadmap; Sprint Planning. Desktop uses the requested 2–2–1 arrangement; small screens stack. Each card has purpose, quality guidance, an example, prerequisites and a direct link. Refinement remains linked from Stories. The remaining destinations are discoverable in expandable Planning, Delivery and Workspace groups. Actual initiative editing authority controls regeneration links; internal workspace-administrator authority controls integration administration and boundary creation. These are existing authorization requirements, not experience-based products.

Historical profiles remain stored. The retired experience-evaluation address redirects to planning; its authenticated mutation API returns 410 instead of creating/recalibrating profiles. Active intake/document guidance no longer branches on experience; legacy helper arguments are inert. Settings provides an explicit optional tour instead of experience selection. Tours never auto-start. Product Owner can open the existing Roadmap and version-history views without a historical working-role restriction.

AI assistance continues through existing bounded, budgeted, explicit suggestion services. The guide and manual planning make no AI calls. Deterministic checks continue to govern generation/readiness, permission, approval and commitment. AI receives no new authority or automatic apply path.

## Evidence and limits

Focused navigation, compatibility routing and guidance tests passed. Local development guide checks verified 14 viewport configurations without horizontal overflow, desktop 2–2–1/mobile stack, and five native Tab/Enter selections and direct-entry links at 320px and 1280px. Screenshots were inspected. The responsive checker now rejects browser error pages/missing application content rather than reporting a false pass. Public demo rendering uses non-credential placeholders only in the existing development demo runner; protected routes still require verified sessions.

These layout/keyboard checks do not substitute for signed-in deployed customer journeys. Staging real-data manual planning and permission tests, deployment checks, and final signed-in desktop/mobile acceptance remain separate evidence.
